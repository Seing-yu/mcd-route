**正文结构**（照这个骨架写，700-1200 字）

```markdown
## 一、我为什么做这个

麦当劳 MCP 出来之后，参赛作品里 101 个项目有 60% 在做「怎么点最便宜」。
但我真正每天纠结的是另一件事：**今晚点外卖，还是自己跑一趟？**

于是我去翻了 35 个 Tool 的使用统计，发现 `delivery-*` 和 `query-nearby-stores`
这组几乎没人用——**能送到你家的店，和离你最近的店，常常不是同一家。**
而优惠券是绑门店的。

## 二、这个决策比想象中复杂

| | 外送 | 到店自取 |
|---|---|---|
| 配送费 | 有 | 无 |
| 起送价 | 硬门槛 | 无 |
| 券可用性 | 部分券用不了 | 部分券仅到店可用 |
| 时间成本 | 等餐 | 往返 + 出餐 |

## 三、我做的取舍：不追求最优，追求「一定能成交」

大多数省钱助手会把所有券无差别参与优化，报出一个你根本用不了的低价。
我做了三个保守选择：

1. **只取单张最优券，不叠加**
2. **券的场景限制严格生效** —— 到店券不进外送的计算
3. **数据缺失就明说不计入**，绝不估算一个数填上

时间成本也做成了参数：`--minute-cost 0` 表示不在乎时间，
`1.67` 约等于时薪 100 元。**结论会随你的时间价值观变，而不是给一个固定答案。**

## 四、踩的坑（这才是本文最有价值的部分）

1. **金额单位按工具区分**：只有 `calculate-price` 返回「分」，
   `query-meals` 已经是「元」。混用会让每个金额差 **100 倍**。
   这个坑文档不写，只能靠真实调用撞出来。
2. 券要四路查全，`available-coupons` 的券不先领就不在卡包里
3. 门店券绑门店，所以两个渠道必须分别查
4. `query-nearby-stores` 的 `city` 和 `keyword` 必须成对传
5. 响应不一定是纯 JSON，是「散文 + 内嵌 JSON」的混合文本

## 五、代码怎么跑

零依赖，Python 3.8+：

    cd skills/mcd-route/scripts
    python decider.py --pretty     # 看决策结果
    python selftest.py             # 53 项自测

## 六、顺手说说合规

《麦当劳 MCP 服务规则》第六条明确禁止「利用脚本、爬虫或任何自动化工具调用本服务」。
我没有靠嘴解释「我们是人机交互不是爬虫」，而是把约束写进了代码：
单会话调用上限 120 次、两次调用间隔 ≥ 0.35 秒、不提供任何批量接口。
规则原文快照也存进了仓库 `docs/`。

## 七、最后

觉得「点外卖前先算一笔」有意思的话，点个 Star ⭐
👉 https://github.com/swing-yu/mcd-route

（仓库名待你最终确定后替换）
```

## 四、给朋友的话术（决定 star 转化率的关键）

Star 转化率取决于「对方是否觉得这东西对他有用」。按人分三类：

| 对方是 | 怎么说 |
|---|---|
| 程序员朋友 | 「零依赖纯标准库，能直接跑，53 项自测。你 star 一下我看看排名能到多少」 |
| 经常点外卖的朋友 | 「你算过外送和到店哪个划算吗？我写了个能算的，star 一下我请你吃饭（券）」 |
| 麦当劳常客 | 「你那张券可能根本用不了——外送用不了门店券的。我写了个能查的」 |

**关键**：别群发同一段话。**针对每个人的一句话，比十段通用文案有效。**
